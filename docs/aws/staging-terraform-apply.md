# Protected staging Terraform Apply

The [Terraform validation workflow](../../.github/workflows/terraform-validate.yml) can publish a saved staging Plan only after the staging Environment approval, State-VersionId check, ownership checks, budget/window gate, plan summary, and protected-resource action guard pass. It encrypts the binary Plan with AES-256-GCM using the protected `TF_PLAN_ENCRYPTION_KEY` Environment secret. The artifact contains only ciphertext and non-secret metadata, is retained for one day, and the runner removes its local Plan and tfvars files after upload.

The separate [Apply workflow](../../.github/workflows/staging-terraform-apply.yml) accepts the successful Plan run ID, exact source commit, Plan SHA-256, State VersionId, and approved budget/window inputs. It verifies the source was a successful manual Plan run from `main`, checks that the Plan job and unexpired artifact exist, downloads the ciphertext, and verifies its authenticated decryption and metadata against the submitted approvals. It checks the current S3 State VersionId again, initializes the original source commit and staging workspace, reruns `guard_staging_plan_actions.py`, and invokes `terraform apply` with the verified saved Plan file only.

Both jobs require the protected `staging` Environment and the `staging-vpc` runner. The Apply job requires a dedicated `AWS_APPLY_ROLE_ARN`, different from the Plan and service Deploy roles. M1 must provision and review this role's minimum AWS and Kubernetes permissions against the approved Plan; this change does not create the role or authorize an Apply. M1 must also set `TF_PLAN_ENCRYPTION_KEY` as an Environment secret before producing a Plan artifact. Generate a 32-byte key locally (for example, `openssl rand -base64 32`), store the same value in an approved vault, and place it directly in the protected Environment; never commit it or print it in Actions logs. Keep the same key available until the one-day artifact expires or has been applied, then rotate it through the protected secret-management process.

Before approving a Plan, M1 must download the encrypted artifact on a trusted machine, verify the source run, commit, Plan SHA-256, and State VersionId against the run summary, then decrypt with the protected key and inspect `terraform show -no-color` output in a mode-600 local file. The plaintext Plan must stay local and be removed after review; it must not be pasted into GitHub, chat, or an unencrypted artifact.

An Environment approval is required for both Plan and Apply runs. Approving a Plan does not approve an Apply. A failed State-version, artifact, digest, metadata, target, budget, or action-guard check stops the workflow before Apply. The workflow does not import, migrate State, create an Apply Role, or bypass GitHub Environment approval.
