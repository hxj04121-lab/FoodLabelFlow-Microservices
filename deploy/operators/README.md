# Staging operators

M1 independently owns cert-manager v1.21.2, RabbitMQ Cluster Operator v2.22.3, and Messaging Topology Operator v1.20.2, including their cluster-scoped CRDs, roles, webhooks, and Deployments. Their reviewed release URLs and byte locks are recorded in [`rabbitmq/operator-manifests.lock`](rabbitmq/operator-manifests.lock). The protected [`install-rabbitmq-operators.yml`](../../.github/workflows/install-rabbitmq-operators.yml) workflow is main-only, requires the staging Environment and staging-vpc runner, validates the dedicated install identity and budget/window, checks every locked target for prior ownership, then uses `kubectl create` in dependency order. Both RabbitMQ bundles declare `rabbitmq-system` with different labels; the workflow creates that namespace from the Cluster Operator bundle and omits only the duplicate Namespace document from the already hash-verified Topology Operator bundle. Any existing target, failed read, failed digest, or failed readiness check stops the run; the workflow does not upgrade, replace, or clean up objects. It does not include the Keycloak Operator. M1's CloudShell procedure remains a fallback only after separate approval.

After the protected Terraform foundation and independent M1 Operator installation are complete, the M5 RabbitMQ workflow creates the reviewed `RabbitmqCluster`, users, permissions, and topology resources using only the limited namespace-scoped deployment RoleBindings. Review the manifests and render the topology chart offline with `helm template rabbitmq-topology deploy/helm/rabbitmq-topology --namespace rabbitmq`; the chart's ordered `00-exchanges`, `10-queues`, `20-bindings`, and `30-policies` templates are the only topology definition.

The business users have no management tag and use Operator-generated per-service credential Secrets. The isolated `staging-smoke` user alone has the management tag needed for a publish/consume smoke check. The Messaging Topology Operator automatically applies its cache label to generated credential Secrets; user-provided credential Secrets would instead need `rabbitmq.com/topology-operator: "true"` and are not used here. Do not print, commit, or log Secret data.

The Keycloak realm and org/role/client claims remain owned by G1-M4 (`deploy/keycloak`). After the RDS endpoint and runtime credentials are available, render `deploy/operators/keycloak/keycloak.yaml.tmpl` with `RDS_ENDPOINT`, create the `keycloak-db` Secret from the protected staging environment, and apply the Keycloak custom resource. Do not commit rendered output or Secret data.
