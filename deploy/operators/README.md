# Staging operators

RabbitMQ staging is prepared by `.github/workflows/deploy-rabbitmq.yml`. It is manual, main-only, runs on the private staging VPC runner, requires the protected `staging` Environment and approved-spend window, and never creates namespaces. Before dispatch, Terraform must have installed EBS CSI/`ebs-gp3` and the six missing namespaces; general must have three Ready nodes across both AZs and Compliance must have two Ready `c6i.large` nodes across both AZs.

The workflow installs cert-manager `v1.21.2`, RabbitMQ Cluster Operator `v2.22.3`, then Messaging Topology Operator `v1.20.2`, using the separate `AWS_OPERATOR_INSTALL_ROLE_ARN`. That existing IAM role must trust only the protected GitHub OIDC environment and receive cluster-admin access through the optional `rabbitmq_operator_install_role_arn` Terraform setting. This is a cluster-wide permission expansion and must be separately approved by M1. The regular `AWS_DEPLOY_ROLE_ARN` is used for RabbitMQ workload resources and smoke testing.

Deployment order is Cluster/three EBS PVCs, per-service and smoke Users, Permissions after User readiness, then the chart's Exchanges, Queues, Bindings, and Policies in dependency order. User credentials are generated into Kubernetes Secrets by the Cluster Operator and read only by the workflow at runtime; never commit or upload their values. The isolated `staging-smoke.smoke` queue is quorum and durable, and the smoke message uses persistent delivery mode. PVC retention is `Retain` both on the StorageClass and StatefulSet; cleanup requires separate data-retention review.

The Keycloak realm and org/role/client claims remain owned by G1-M4 (`deploy/keycloak`). After the RDS endpoint and runtime credentials are available, render `deploy/operators/keycloak/keycloak.yaml.tmpl` with `RDS_ENDPOINT`, create the `keycloak-db` Secret from the protected staging environment, and apply the Keycloak custom resource. Do not commit rendered output or Secret data.

The topology CRs follow architecture v3 §6.3–6.4; the chart is rendered locally by Helm before apply. Operators and workloads require CRDs/webhooks to be ready before applying their custom resources. No live deploy is implied by static workflow or chart validation.
